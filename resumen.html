Portal de Gestión Documental de Proveedores

Sistema enterprise para la inscripción, verificación, aprobación, actualización e historial de proveedores naturales y jurídicos de la Universidad Autónoma de Bucaramanga.

Versión 4.8 · Producción Cifrado AES-256-GCM Ley 1581 de 2012

1. Resumen ejecutivo

El Portal de Gestión de Proveedores es la plataforma oficial de la UNAB para administrar el ciclo de vida documental de sus proveedores: desde la inscripción inicial hasta la actualización anual, incluyendo verificación, aprobación, inscripciones, rechazos e histórico permanente. Reemplaza flujos manuales basados en correo y carpetas compartidas por un workflow trazable, cifrado de extremo a extremo y alineado con la normativa colombiana de protección de datos.

4. Continuidad operativa y recuperación ante desastre

💾 Backups automáticos

Cada 12 horas (2 AM / 2 PM Colombia). Retención: 14 copias + mirror incremental de archivos cifrados.

🩹 Self-healing

Verificación integrity_check al arranque. Si la BD está corrupta, restaura automáticamente el backup más reciente.

🔄 Mirror de archivos

Los .enc son inmutables: el mirror conserva todo lo que haya existido, incluidos reemplazados o borrados.

♻️ Restauración guiada

Snapshot de seguridad previo + recuperación de archivos físicos faltantes desde el mirror. Servicio reinicia solo (Railway).

5. Calidad del software

Funcionamiento — Antes de que cualquier cambio llegue a los usuarios, el sistema se "auto-examina" con 61 verificaciones automáticas que revisan el cifrado, el ingreso, los documentos y los respaldos. Si una sola verificación falla, el cambio se bloquea y no se publica. Es como tener un inspector de calidad permanente que trabaja en cada modificación, a toda hora y sin omitir pasos.

IndicadorQué significaPor qué da confianza
61 tests automatizadosVerificaciones que el sistema ejecuta solo, cada vez que se modifica el códigoDetectan el error antes de que lo vea un usuario y evitan que se rompa lo que ya funcionaba
7 suites de pruebasLos tests están organizados por área: seguridad, acceso, documentos, respaldos, ciclos, configuración y gestiónCada proceso crítico del negocio tiene su propia verificación independiente
~35% de cobertura en server.jsPorción del código del servidor verificada por tests, concentrada en los flujos críticos del negocioEs un nivel sano para un sistema de este tamaño: lo importante no es cubrir todo el código, sino el código que más duele si falla
77% de cobertura en criptografíaEl módulo que protege documentos y contraseñas está verificado casi en su totalidadLa parte más sensible del sistema es, a la vez, la más probada

Suites implementadas: security (AES/SHA/contraseñas) · auth (login, anti-enumeración, rutas) · documentos (subida magic-bytes, verificación, aprobación, rechazo) · backups (crear, verificar, descargar, anti path-traversal) · ciclos (históricos, filtros, ZIP) · configuración (fecha fija, recalcular, ejecutar/forzar vencimientos) · gestión-proveedor (tipo persona, evaluación, notas, recordatorios).

¿Dónde se ejecutan? En la nube (GitHub Actions), automáticamente con cada cambio y sobre dos versiones de Node.js. Un cambio con el check en rojo no puede publicarse: el flujo verde es el candado de calidad del portal.

7. Flujo del proceso

Leyenda: 🟣 paso normal · 🟡 transición / alerta · 🔴 rechazo / bloqueo · 🟢 éxito. Cada documento pasa por: subida → validación → verificación → aprobación → vencimiento → archivo histórico.

7.1 Proceso normal — inscripción nueva

📝 INSCRIPCIÓNProveedor crea cuenta (o lo crea el admin), acepta Habeas Data, completa datos y tipo de persona
→
📤 CARGASube documentos en PDF o marca "No aplica" en los opcionales
→
🔍 VERIFICACIÓNAdmin marca verificado cada documento; todos verificados → pasa a Aprobación
→
📋 APROBACIÓNAdmin aprueba documentos y aprueba la Evaluación Inicial → pasa a Inscripción
→
🖋️ INSCRIPCIÓNAdmin asigna Fecha Movimiento (N° registro); se crea el ciclo y se asigna a los documentos
→
🏁 REGISTRADOProveedor activo; documentos con fecha fija de vencimiento

7.2 Rechazo de un documento

🔍 VERIFICACIÓNAdmin revisa y detecta error en un documento
→
❌ RECHAZOAdmin rechaza con motivo; el proveedor recibe correo
→
🗑️ ELIMINARProveedor debe eliminar el documento rechazado (requisito para recargar)
→
📤 NUEVA CARGAProveedor sube la versión corregida
→
🔁 CONTINÚAEl documento re-entra al flujo de verificación

⚠️ Si el proveedor ya estaba en Aprobación, Inscripción o Registrado, el rechazo de un documento lo devuelve a Verificación y limpia los datos de gestión.

7.3 Rechazo de Evaluación Inicial — inscripción nueva

📋 APROBACIÓNLa evaluación no cumple; los documentos deben estar aprobados para aprobarla
→
❌ RECHAZO EVALUACIÓNAdmin rechaza con motivo; correo al proveedor
→
⛔ RECHAZADOTodos los documentos activos pasan a rechazados; etapa → Rechazado
→
🗑️ LIMPIEZAProveedor elimina rechazados (o el admin usa Reiniciar proceso)
→
📤 RECARGASube de nuevo y el flujo reinicia en Verificación

7.4 Rechazo de Evaluación Inicial — proceso de actualización

🔄 ACTUALIZACIÓNProveedor en actualización (tipo_gestion = actualizacion)
→
❌ RECHAZO EVALUACIÓNAdmin rechaza con motivo
→
🔁 A VERIFICACIÓNDocumentos rechazados, pero el proveedor NO queda bloqueado: etapa → Verificación
→
📤 CORRECCIÓNElimina rechazados y sube corregidos
→
📋 RE-APROBACIÓNCon todo aprobado, se aprueba evaluación y continúa la inscripción

7.5 Actualización anual de documentos

🏁 REGISTRADOProveedor activo con documentos vigentes
→
🔄 SOLICITUDAdmin solicita actualización (con mensaje); correo y recordatorio al proveedor
→
📦 ARCHIVADODocumentos activos y evaluación se mueven al histórico (carpeta del ciclo)
→
🔍 VERIFICACIÓNProveedor define tipo de persona y sube documentación nueva
→
📋 APROBACIÓN + 🖋️ REGISTROAprobación de docs y evaluación; nuevo ciclo con nueva Fecha Movimiento
→
🏁 REGISTRADOProveedor activo para el nuevo período

7.6 Vencimiento automático (cron diario 12:00 a. m.)

⏰ DETECCIÓNDocumentos con fecha_vencimiento ≤ ahora − 5 h
→
📦 ARCHIVADOSe mueven a histórico automáticamente
→
⛔ RECHAZOSi el proveedor registrado queda sin documentos activos → Rechazado + correo
→
🔓 REACTIVACIÓNProveedor define tipo de persona y sube documentación nueva

7.7 Vencimiento forzado (acción del admin)

⚡ ACCIÓNConfiguración → "Forzar vencimiento de todos los documentos" (doble confirmación)
→
📦 ARCHIVADO TOTALTodos los documentos activos de todos los proveedores pasan a histórico
→
⛔ RECHAZOProveedores afectados pasan a Rechazado con notificación
→
🔓 REACTIVACIÓNCada proveedor recarga su documentación (flujo 7.6)

⚠️ Acción irreversible: se recomienda crear un backup manual antes (Configuración → Backups).

7.8 Reinicio de proceso desde estado Rechazado

⛔ RECHAZADOProveedor bloqueado con documentos rechazados
→
♻️ REINICIARAdmin ejecuta "Reiniciar proceso"
→
🧹 LIMPIEZASe elimina la evaluación; documentos quedan rechazados con comentario de corrección; etapa → Verificación
→
📤 RECARGAProveedor elimina rechazados y sube nueva documentación
